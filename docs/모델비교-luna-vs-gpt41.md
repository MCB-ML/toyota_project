# 모델 비교 — GPT-5.6 Luna vs GPT-4.1

**결론: 기본 모델을 GPT-4.1로 유지한다.** 같은 코드·같은 평가 52건으로 나란히 재니
확인이 필요한 답이 **2건 대 7건**, 값이 틀린 답이 **0건 대 1건**이었다. Luna는 2.8배
빠르지만, 이 제품에서 틀린 숫자 한 건의 비용이 대기 시간 30초보다 크다.

측정일 2026-08-11. 대상 커밋 `7002a99`(양쪽 동일).

---

## 1. 왜 쟀나

이 제품의 핵심 실패는 **"쿼리는 성공하고 표도 멀쩡한데 숫자만 다른 것"**이다. 오류가
안 나므로 사람 눈으로 안 걸린다. 그래서 평가 52건을 GOLD 결과와 대조하는 하네스를
두고, **같은 질문을 여러 번 던져 답이 갈리는지**까지 본다.

Luna로 전환하면서, 모델이 바뀌면 이 흔들림이 어떻게 달라지는지 확인이 필요했다.

## 2. 어떻게 쟀나

| | |
|---|---|
| 평가 항목 | 52건 (BI 화면 질문 · GOLD SQL 결과가 정답) |
| 반복 | 항목당 2회. 두 답이 다르면 `변동`으로 표시 |
| 판정 | `OK` / `변동`(값은 맞으나 실행마다 다름) / `불일치`(GOLD에 없는 값) |
| 코드 | **완전히 동일**. 하네스에 `--model=` 을 붙여 모델만 바꿨다 |

같은 코드로 재는 것이 중요하다. 처음 Luna를 쟀을 때는 4.1 측정보다 수정이 더 들어간
상태였는데, 그 상태로 비교하면 차이가 모델 때문인지 코드 때문인지 갈리지 않는다.

## 3. 결과

| | 확인 필요 | 그중 값이 틀림 | 소요 |
|---|---|---|---|
| **GPT-4.1** (temperature 0) | **2건** (24·28) | **0건** | 40분 17초 |
| **GPT-5.6 Luna** (temperature 1 고정) | **7건** (16·25·28·29·33·45·49) | **1건** | 14분 29초 |

겹치는 항목은 **28번 하나뿐**이다. 즉 Luna에서 추가로 걸린 5건은 Luna에서만 생긴다.

### 특정 질문이 약한 게 아니다

Luna 전수를 세 차례 돌렸는데 걸린 항목이 매번 달랐다.

| 회차 | 걸린 항목 |
|---|---|
| 1차 | 1 · 2 · 3 · 4 · 5 · 26 · 27 · 29 · 46 |
| 2차 | 16 · 25 · 28 · 29 · 33 · 45 · 49 |
| 3차 | 15 · 16 · 24 · 25 · 26 · 28 · 37 · 45 · 46 · 49 · 50 |

겹치는 건 거의 없다. **전체가 조금씩 흔들린다**는 뜻이다. 반대로 4.1은 두 차례 모두
같은 자리(24·28)만 걸렸다.

## 4. 원인

### 4-1. Luna는 temperature를 0으로 내릴 수 없다

```
temperature 0.2 → 400  "Only the default (1) value is supported"
max_tokens      → 400  "Use 'max_completion_tokens' instead"
top_p           → 400  "not supported with this model"
```

4.1은 `temperature: 0`을 받는다. 같은 입력에 같은 답이 나오도록 눌러 둘 수 있다.
Luna는 그 손잡이가 없다. 이 제품은 **같은 질문에 같은 답**이 나와야 하는데, 모델이
그것을 보장할 수단을 주지 않는다.

### 4-2. seed로 대신해 봤지만 듣지 않았다

Luna는 `seed`를 받는다. 호출 하나만 보면 확실히 듣는다.

```
같은 질문 6회 · seed 고정 : 대전 대전 대전 대전 대전 대전   (1종)
같은 질문 6회 · seed 없음 : 대전 부산 부산 대전 대전 서울   (3종)
```

그런데 **파이프라인 전체로는 차이가 없었다.** 평가 8건을 각 5회씩 양쪽으로 돌린 결과:

| 번호 | seed 있음 | seed 없음 |
|---|---|---|
| 16 | 2종 | 2종 |
| 24 | OK | OK |
| 25 | OK | OK |
| 28 | 2종 | **OK** |
| 29 | 2종 | 2종 |
| 33 | 2종 | **OK** |
| 45 | 4종 | 3종 |
| 49 | **OK** | 2종 |
| **흔들린 항목** | **5건** | **4건** |

오히려 없는 쪽이 조금 나았다. **질문 하나가 LLM을 여러 번 부르고 그 입력이 실행마다
조금씩 달라서**, 같은 seed라도 같은 지점에서 갈리지 않는다. 그래서 되돌렸다
(커밋 `82b7869` → `662124a`). 이유는 `service/backend/llm/models.js`에 남겨 두었다 —
호출 하나만 보면 잘 듣는 것처럼 보이므로, 안 적어두면 다음 사람이 같은 것을 다시 시도한다.

### 4-3. 남은 흔들림은 서버가 대신 정해 줄 수 없는 자리다

Luna에서 남은 6건의 흔적을 보면 두 갈래다.

**경로가 갈린다 (16 · 24 · 49)** — 같은 질문이 인증 리포트로 갔다가 지표 경로로 갔다 한다.

```
No.16  run1·3 → 인증 리포트 activity_funnel_status (9행)
       run2   → 지표 경로 (12행)
No.49  run1·3 → 인증 리포트 (15행, 전체 컬럼)
       run2   → 지표 경로 (1행)
```

**같은 리포트인데 표 모양이 갈린다 (28 · 29 · 45)** — 질문에 맞게 접힌 표와 원본 상세
전체가 번갈아 나온다.

```
No.28  run1 [딜러, 출고, 출고목표, 출고진행률]
       run2 [연도, 월, 브랜드, 딜러, 전시장, 팀, 출고, 출고목표, 출고진행률]
No.29  run1 7행   [활동유형, 일일활동실적, 일일잔여타겟]
       run2 112행 [연도, 월, 일, 브랜드, 딜러, 전시장, 팀, 활동유형분류, …]
```

둘 다 **질문 문장에 근거가 없는 선택**이다. "출고 목표 대비 출고 건수를 게이지로"라는
질문은 표에 연도·월 열을 넣을지 말지를 말해 주지 않는다. 근거가 없는데 서버가 정하면
근거 없이 답을 바꾸는 것이고, 그건 실제로 더 나빠졌다(6장 참고).

## 5. 서버 규칙으로 고칠 수 있었던 것은 고쳤다

모델 탓으로 돌리기 전에, 질문에 근거가 있는 것은 전부 서버가 정하도록 바꿨다.
아래는 이번 라운드에 실제로 고친 것이다.

| 평가 | 증상 | 원인 | 조치 |
|---|---|---|---|
| 1~5 | 한 실행은 정답, 다른 실행은 "데이터 없음" | 질문의 `렉서스강남`(붙여씀)과 DB의 `렉서스 강남`(띄어씀)이 정확히 일치하지 않아 **0행** | 인증 리포트 경로에만 있던 값 정규화를 지표 경로에도 걸었다 |
| 13 | 4회 중 1회가 다른 숫자 | 실적만 퍼널 기준이고 타겟·취소는 아니어서 한 표 안에서 모집단이 섞였다 | 한 답 안에서 모집단이 섞이면 맞춘다 |
| 34 | 다섯 열을 물었는데 넷만 나옴 | 별칭 없는 열은 이름이 적혀 있어도 매칭에서 빠졌다 | 이름 자체를 근거로 삼되 **더하기로만** |
| 47 | 전체 85행이 걸러진 결과인 양 나감 | `3회차` 필터가 실행마다 붙었다 말았다 | 계약이 선언한 단위를 읽어 서버가 채운다 |
| 51 | 원값 5행과 비중 6행이 번갈아 | 시맨틱에 PMA 비율 지표가 **없다** | 비율 컬럼이 유일할 때만 그 리포트로 보낸다 |
| 52 | 같은 리포트가 300행과 380행 | `누적 취소율`·`A 그룹` 조건이 붙었다 말았다 | 허용값이 선언된 필터는 질문에 있으면 채운다 |

이 정규화가 없었다면 4.1도 같은 자리에서 틀렸을 것이다. **1~5번의 띄어쓰기 문제는
4.1이 우연히 띄어쓰기를 넣어 줘서 안 드러났을 뿐, 보장된 동작이 아니었다.**

## 6. 시도했다가 되돌린 것 — 근거 없이 정하면 더 나빠진다

| 시도 | 결과 |
|---|---|
| "퍼널을 안 물었으면 퍼널 지표를 쓰지 마라" | No.5를 깼다. `계약건수`는 어느 쪽으로 읽어도 맞는 질문이라 GOLD가 두 답을 **모두** 정답으로 둔다. 규칙이 정답을 내던 지표를 바꿔버렸다 → **"한 답 안에서 모집단을 섞지 마라"**로 좁혔다 |
| No.25를 인증 리포트로 재라우팅 | 변동(1행/3행)이던 것이 3회 3종 불일치가 되고 위젯 대신 문장이 나왔다 → 되돌렸다 |
| 질문이 부른 축을 표시 컬럼에 남기기 | 넣기 전 52건에 걸어 보니 **지금 통과 중인 6건을 건드려 1건을 고치는** 거래였다 → 넣지 않았다 |
| Luna에 seed 고정 | 4-2 참고 → 되돌렸다 |

여기서 얻은 작업 규칙 두 가지를 남긴다.

- **규칙은 넣기 전에 평가 52건 전체에 걸어 몇 건이 영향받는지 센다.** 자기 한 건에만
  걸리면 안전하고, 절반이 걸리면 규칙이 틀린 것이다. 이 계측으로 27/52가 걸리는
  잘못된 축 규칙을 걸러냈다.
- **고쳤다고 판단하기 전에 변경 전 코드로 같은 질문을 돌려 비교한다.** 테스트가 다
  통과해도 회귀는 숨는다 — No.34를 고치면서 No.10·11을 깼는데 이 대조로만 드러났다.

## 7. 측정 자체의 한계

전수 한 번의 숫자로 개선을 판정하면 안 된다. Luna 전수의 걸린 건수는 **9 → 7 → 11**로
요동쳤는데, 코드는 그 사이 좋아지기만 했다. 항목당 2회에서는 아슬아슬한 항목이
걸리느냐 마느냐가 사실상 동전 던지기다.

**개선 여부는 같은 항목을 5회 이상, 변경 전/후로 나란히 재야 한다.** 4-2의 seed 표가
그 방식이고, 그렇게 재고 나서야 "효과 없음"이 드러났다. 3회로 쟀을 때는 효과가 있는
것처럼 보였다.

## 8. 결정과 되돌리는 법

**기본 모델은 GPT-4.1이다.** `service/backend/llm/models.js`의 `default: true` 한 줄이
그것을 정한다. Luna와 Claude Sonnet 5는 화면의 모델 선택기에서 그대로 고를 수 있다.

Luna로 다시 옮기려면 그 한 줄을 옮기면 된다. 다만 그때는 이 문서의 3장 수치를 다시
재고 판단하기를 권한다 — 모델이 갱신되면 결과가 달라질 수 있고, 이 측정은
2026-08-11 시점의 `gpt-5.6-luna-2026-07-09`에 대한 것이다.

자격정보는 루트 `.env`가 아니라 **`service/.env`**에 있다.
